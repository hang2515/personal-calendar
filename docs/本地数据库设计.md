# 本地数据库设计

当前应用无需登录即可使用，日历与打卡保存在设备内的 Room 数据库 `personal-calendar-local.db`。数据库版本为 5；用户可主动开启 AWS 云备份。系统自动备份及设备迁移备份仍关闭。

月度进度以所选月份的全部计划日为分母，包含未来安排；创建当月从创建日起算，暂停和重复星期按历史生效规则计算。分子只计截至今天真实完成的计划日。列表批量读取规则到月底，以包含已保存的次日生效变更；不改变数据库结构或既有打卡记录。

## 数据表

| 表 | 主键 | 主要字段与用途 |
| --- | --- | --- |
| `calendars` | `id`（UUID） | 名称、开始日期、重复星期位图、暂停状态、提醒开关与分钟数、图标和颜色。 |
| `schedule_changes` | `calendarId + effectiveDate` | 记录某天起生效的星期位图；`0` 表示暂停期间不安排计划。按生效日期回放规则，避免编辑后改写过去的月历。 |
| `check_ins` | `calendarId + localDate` | 每个日历在当地日期最多一条打卡；重复打卡不会重复计数。 |
| `local_state` | 单行 `id = 1` | 数据集 ID、本地版本、绑定账号、备份开关、已备份版本、最近备份时间和云端 ETag。 |

`check_ins` 和 `schedule_changes` 都引用 `calendars.id`，删除日历时级联删除对应记录。`check_ins.localDate` 另建索引，支持查询当天所有日历的完成情况；两个复合主键支持按日历和日期查询。日期使用 `YYYY-MM-DD` 文本，星期位图以周一为第 0 位、周日为第 6 位。当前业务时区固定为 `Asia/Shanghai`，提醒分钟数为当天 `0..1439`。

## 写入与历史规则

- 创建日历时，在同一数据库事务内写入日历和初始规则。名称、星期位图、提醒分钟数及图标颜色在仓储层校验。
- 修改重复星期或暂停状态时，若今天已经打卡，新规则从明天生效；否则从今天生效。过去的打卡和计划状态保持原样。
- 撤销今天的打卡时，若此前有因打卡而顺延到明天的规则变更，会在同一事务内把该规则改为今天生效，并删除明天的顺延记录。
- 删除日历时，数据库级联删除规则和打卡；事务提交后取消对应本地提醒。需要恢复时只能选择仍包含这些记录的完整备份。
- 成功的业务修改在同一事务内递增 `localRevision`；重复打卡和无实际变化的更新不会递增。上传完成仅记录该快照版本，上传期间的新修改仍为待备份。

## 升级与数据边界

现有 `1→2→3→4→5` 迁移保留日历和打卡，逐步补齐暂停、提醒、图标、颜色及备份状态。4→5 为旧安装创建新的数据集 ID，默认未绑定且备份关闭。升级不会破坏性重建；结构快照保存在 `app/schemas`。

三张业务表不增加用户 ID，整份本地数据通过 `local_state.boundAccountSub` 绑定备份账号。退出登录保留业务数据并关闭备份；换账号必须确认重新绑定或恢复。密码和令牌不进入 Room，AppAuth 状态使用 Android Keystore 加密后保存。

恢复先校验备份，再检查预览时的本地版本，在单事务内批量替换三张业务表并更新状态；失败回滚。完整备份是 JSON，不复制正在使用的 SQLite/WAL 文件。详细接口、上限和部署见 [AWS 云备份部署](AWS云备份部署.md)。
